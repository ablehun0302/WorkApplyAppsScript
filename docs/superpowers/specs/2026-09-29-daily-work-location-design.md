# 날짜별 근무지 신청 설계

작성일: 2026-09-29

## 목적

근무자가 근무지를 매일 다르게 신청할 수 있게 한다. 지금은 근무자 한 명당 근무지가
하나뿐이라, 월~금은 신세계푸드에 가고 토·일은 BGF에 가는 사람을 표현할 방법이 없다.
근무자들은 이걸 신청서의 자유 메시지 칸에 글로 적어 보내고 있고(`WorkerView.html:34`의
placeholder가 "월화수목금_신세계푸드/토일_BGF 신청합니다"를 예시로 안내한다),
관리자가 그 글을 읽고 손으로 처리한다.

## 핵심 결정

**날짜별 근무지는 기본 근무지의 예외로만 저장한다.** 사람 단위 근무지(G열 희망,
H열 관리자 지정)를 그대로 두고 "기본 근무지"로 삼은 뒤, `Data` 시트 F열 `shiftsJSON`의
날짜 항목에 `location`이 있을 때만 그날의 근무지를 덮어쓴다.

기본값과 같은 값은 저장하지 않는다. 이 규칙이 만드는 결과가 중요하다:

- 기존 데이터는 전부 `location`이 없으므로 그대로 기본 근무지로 동작한다. 마이그레이션이
  필요 없다.
- 관리자가 "이 사람 통째로 BGF로 이동"(`setAdminLocation`)을 실행하면, 예외 지정을 하지
  않은 날짜들이 자동으로 따라간다. 매번 `location`을 채워 저장하면 이 기존 기능이
  무력화된다.
- 드롭다운에서 기본값과 같은 값을 고르는 것이 곧 예외 해제다. 별도 "초기화" 버튼이 필요 없다.

## 데이터 모델

`Data` 시트 F열 `shiftsJSON`:

```js
[{ date: "2026-09-30", day: true, night: false, location: "BGF푸드_진천" },  // 예외 지정
 { date: "2026-10-01", day: true, night: true }]                             // 기본 근무지 사용
```

근무지는 **날짜 단위**다. 같은 날 주간과 야간을 둘 다 신청해도 근무지는 하나다.

G열 `locationsJSON`, H열 `adminLocation`은 구조를 바꾸지 않는다. 역할만 "기본 근무지"로
재정의된다.

### 실효 근무지 계산

지금 여덟 군데에 흩어져 있는 `adminLocation || locations[0]` 한 줄을, 날짜 인자를 받는
함수 하나로 모은다. 서버(`WorkSystemSheet.gs`)와 클라이언트(`AdminView.html`)에 각각 하나씩
둔다.

```js
effectiveLocation(rec, dateStr)
  = (rec.shifts.find(s => s.date === dateStr) || {}).location
    || rec.adminLocation
    || rec.locations[0]
    || ''
```

### 배치 확정 후의 판정 기준

배치판에서 근무지를 판정하는 기준이 대상에 따라 다르다.

| 대상 | 판정 기준 |
|---|---|
| 미배치 신청자 칩 | `Data` F열의 그날 `location` → 없으면 기본 근무지 |
| 배치 확정 명단 | `Assign` 시트 K열 → **비어 있으면** `Data` 기준 실효 근무지 |

K열 폴백을 빼면 안 된다. K열은 나중에 추가된 컬럼이라 그 이전 배치 기록은 값이 비어
있고(`ApplyWorkerSite/docs/DESIGN.md`의 2026-09-04(2) 항목), 폴백 없이 `a.location`만
보면 그 옛 기록들이 모든 근무지 탭에서 사라진다. 지금 코드가 `Data`를 우선 참조하는
것(`AdminView.html:2308`)도 같은 이유에서 나온 처리다.

이렇게 하면 관리자가 배치를 확정한 뒤에 근무자가 신청 근무지를 바꿔도, 확정된 배치는 그
탭에 그대로 남는다. 지금은 배치 확정 기록도 `Data`를 다시 읽어 판정하기 때문에
(`AdminView.html:2308`) 근무자가 신청을 바꾸면 배치 기록이 소리 없이 다른 탭으로 이동한다.

### 신규 함수

```js
setShiftLocation(key, date, location, adminPw)
```

관리자가 배치판 날짜 칸 팝업에서 근무지를 바꿀 때 호출한다. 동작:

1. F열 해당 날짜 항목의 `location`을 설정하거나(기본 근무지와 다르면) 삭제한다(같으면).
2. 그 날짜에 이미 배치가 있으면 `Assign` K열도 함께 갱신한다. 주간·야간이 둘 다 배치되어
   있으면 둘 다 갱신한다.

근무자가 신청 화면에서 바꾸는 경우와 달리 `Assign`을 함께 갱신하는 이유는, 이것이 관리자
본인의 결정이기 때문이다.

`requireAdmin_(adminPw)`와 `LockService`를 기존 저장 함수들과 동일하게 적용한다.

### 손대지 않는 것

`removeCanceledAssignments_():165`는 `(date, shift)` 조합만 비교하므로 그대로 둔다.
근무지가 바뀌어도 신청 취소로 오인하지 않는다.

## 근무자 신청 화면 (`WorkerView.html`)

```
근무 장소(기본)  ◉ 신세계푸드 원남  ○ BGF푸드_진천 …

1주차 (9/29 ~ 10/5)
 9/29(월)  [주간] [야간]
 9/30(화)  [주간✓][야간]  [ 신세계푸드 원남 ▾ ]
 10/1(수)  [주간] [야간]
 10/2(목)  [주간✓][야간✓] [ BGF푸드_진천  ▾ ]
```

- 상단 라디오 레이블: "근무 장소 (해당되는 곳 한 곳만 선택)" → **"기본 근무 장소"**
- `buildDateList()`: 주간/야간이 하나라도 켜진 날짜 행에만 근무지 `<select>`를 표시한다.
  기존 신청의 `location`으로 복원하고, 없으면 기본 근무장소를 선택 상태로 둔다.
- `toggleShift()`: 주간·야간이 둘 다 꺼지면 select를 숨긴다.
- 기본 근무장소 라디오를 바꾸면, **예외 지정이 없던 드롭다운들이 같이 따라간다.**
  예외로 바꾼 날짜는 그대로 유지한다. 판단 기준은 "드롭다운 값이 바꾸기 전 기본값과
  같은가"이다. 따라서 근무자가 기본값과 똑같은 값을 일부러 골라둔 날짜도 함께 따라간다 —
  저장되는 결과가 어차피 같으므로 구분하지 않는다.
- `submitApplication()`: 기본값과 같은 날짜는 `location`을 빼고 전송한다.

근무자가 이미 배치가 확정된 날짜의 근무지를 바꿔도 `Assign` K열은 갱신하지 않는다.
확정된 배치는 관리자가 내린 결정이므로 그대로 둔다. 이 경우 `Data`의 신청 근무지와
`Assign`의 배치 근무지가 달라지는데, 의도된 상태다.

과거 날짜는 지금처럼 수정이 막혀 있다(`buildDateList()`의 `isPast`). 근무지 드롭다운도
같이 비활성화한다.

(`toggleDateSelection():828`이 원본 `lastRecords`를 읽기 때문).

### 날짜 칸 팝업

날짜 칸을 누르면 뜨는 기존 팝업(`showFloorMenu`)에 "근무지" 섹션을 추가한다.

```
  9/30 주간 · 김철수  칸 클릭
  ┌─────────────────┐
  │ 1층  2층  3층    │ ← 기존 (배치 확정)
  │─ 이동수단 ───────│
  │ 버스  자차       │ ← 기존 (배치 확정)
  │─ 근무지 ────────│
  │ 신세계푸드 원남  │ ← 신규 (이 날짜만)
  │ BGF푸드_진천 ✓   │
  │─────────────────│
  │ 지우기           │
  └─────────────────┘
```

층·이동수단 버튼은 `saveAssignment()`를 호출해 배치를 확정시키지만, 근무지 버튼은
`setShiftLocation()`만 호출한다. 배치를 만들지 않는다.

이름 칸 클릭 팝업(`showLocationMenu():544`)은 그대로 둔다. 그쪽은 사람 전체의 기본 근무지를
옮기는 기능이다.

### `location` 유실 방지

`shifts`를 통째로 덮어쓰는 경로가 셋 있고, 모두 날짜별 근무지를 다루지 않는 UI다.

- `saveDateEditChanges()`의 `buildNewShifts():940,946` — `{day, night}`만 복사한다
- `stageAdminAddRecord():1855` → `batchSaveRecords` — 근무자 추가 오버레이
- `openAdminEditShifts()` → `adminUpdateShifts:2009` — 일정수정 오버레이

클라이언트 세 군데를 각각 고치는 대신 **서버에서 기존 `location`을 병합**한다
(`adminUpdateShifts`, `batchSaveRecords`). 누락 위험이 적고, 앞으로 비슷한 경로가 생겨도
자동으로 보호된다.

## 범위 밖

- 전체신청자 목록의 신청/배치 장소 컬럼(`buildApplicantTable():1240`)은 기본 근무지를
  다루는 표라 그대로 둔다.
- 로스터 뷰의 "최근 근무지" 필터는 이미 `Assign` K열을 쓰므로 자동으로 정확해진다.
- 근무자가 배치 확정 후 신청 근무지를 바꿨을 때 관리자에게 알리는 표시는 넣지 않는다.
  필요해지면 별도로 다룬다.

## 검증 체크리스트

배포 후 손으로 확인한다.

### 기존 동작 유지 (회귀)

- [ ] 날짜별 근무지를 한 번도 지정하지 않은 기존 근무자가 전과 똑같이 보인다 —
      배치판 탭, 근무자×요일 표, 신청자 집계, 실근무자 집계 모두
- [ ] 근무자 신청 화면에서 기존 신청을 조회하면 기본 근무장소 라디오가 그대로 복원된다
- [ ] 이름 칸 클릭 → 근무지 이동이 여전히 사람 전체를 옮긴다
- [ ] 날짜 칸 클릭 → 층 선택이 여전히 배치를 확정시킨다
- [ ] 신청 전체 취소, 부분 취소(주간/야간 해제)가 전과 같이 동작한다
- [ ] 과거 날짜는 근무자 화면에서 여전히 수정되지 않는다 (근무지 드롭다운 포함)

### 기본값 fallback

- [ ] 신청 화면에서 근무지를 건드리지 않고 저장하면 F열에 `location`이 들어가지 않는다
- [ ] 기본값과 같은 근무지를 드롭다운에서 고르고 저장해도 `location`이 들어가지 않는다
- [ ] 관리자가 기본 근무지(H열)를 바꾸면, 예외 지정이 없는 날짜들이 전부 따라 이동한다
- [ ] 예외 지정한 날짜는 기본 근무지를 바꿔도 그대로 남는다

### 날짜별 지정

- [ ] 9/30은 BGF, 10/1은 신세계로 신청하면 BGF 탭에 9/30만, 신세계 탭에 10/1만 나타난다
- [ ] 두 탭의 신청자 집계 숫자가 각각 맞다
- [ ] 미배치 칩의 층 드롭다운이 그날 근무지의 층 목록을 보여준다
      (델몬트_원남이면 증평·음성·괴산…, 다른 곳이면 1층·2층·3층…)
- [ ] 델몬트_원남으로 지정한 날짜의 칩에만 이동수단 드롭다운이 나타난다
- [ ] 근무자×요일 표에서 다른 근무지 날짜 칸이 `-`로 보인다

### 배치 확정 후

- [ ] BGF 탭에서 9/30을 배치 확정하면 `Assign` K열에 "BGF푸드_진천"이 들어간다
- [ ] 배치 확정 후 근무자가 9/30을 신세계로 바꿔도, 배치 기록은 BGF 탭에 남는다
- [ ] 같은 상황에서 신세계 탭의 미배치 칩에는 그 사람이 나타나지 않는다 (이미 배치됨)
- [ ] 배치를 취소하면 신세계 탭의 미배치 칩으로 옮겨간다

### `location` 보존

- [ ] 예외 지정이 있는 근무자에게 "신청날짜 수정" 모드로 날짜를 추가/삭제해도
      다른 날짜의 `location`이 남아 있다
- [ ] "일정수정" 오버레이로 저장해도 `location`이 남아 있다
- [ ] 근무자 추가 오버레이에서 기존 근무자 이름을 입력해 덮어써도 `location`이 남아 있다

### 관리자 날짜별 지정

- [ ] 날짜 칸 팝업에서 근무지를 고르면 그 날짜만 다른 탭으로 이동한다
- [ ] 근무지를 고르는 것만으로는 배치가 확정되지 않는다
- [ ] 이미 배치된 날짜의 근무지를 바꾸면 `Assign` K열도 같이 갱신된다
- [ ] 기본 근무지와 같은 값을 고르면 예외가 해제된다 (F열에서 `location`이 사라진다)
